## 장 개요

제01장에서 우리는 `select_device()`에게 "어느 장치로 계산할까"를 물었습니다. 이 장은 그 질문의 속을 들여다봅니다. CPU와 GPU는 무엇이 다르기에 같은 행렬곱을 다른 속도로 처리하는지, 그리고 모델은 어느 메모리에 어떻게 놓이는지를 실측으로 확인합니다.

LLM 실습에서 가장 먼저 부딪히는 벽은 대개 속도가 아니라 **메모리**입니다. 모델이 메모리에 들어가지 않으면 시작조차 할 수 없습니다. 그래서 이 장의 목표는 두 가지 감각을 숫자로 갖추는 것입니다. 하나는 "이 장치가 1초에 몇 번 계산하는가", 다른 하나는 "이 모델이 몇 바이트를 차지하는가"입니다.

| 구분 | 내용 |
|---|---|
| 핵심 질문 | CPU와 GPU는 행렬곱을 어떻게 다르게 처리하며, LLM은 메모리를 얼마나 쓰는가 |
| 실습 결과물 | 행렬곱 속도 측정표(`bench_matmul.csv`)와 그래프, Qwen2.5-0.5B 메모리 계산표 |
| 실습 파일 | `examples/ch02/bench_matmul.py`, `examples/ch02/memory_budget.py`, `examples/ch02/test_ch02.py` |
| 선수 장 | 제01장(가상환경, `select_device()`) |

```text
[연산] CPU·GPU 구조 → 이론 성능 계산 → 행렬곱 실측(GFLOPS)
   ↓
[메모리] RAM·VRAM의 역할 → 모델 크기 계산 → Logits 크기 계산
   ↓
[GPU 조건] Compute Capability → 자료형별 속도 → 가용 VRAM 측정
   ↓
[검증] 계산값과 실측값 비교 + 단위 테스트
```

## CPU와 GPU의 설계 철학

CPU와 GPU는 모두 계산하는 칩이지만, 서로 정반대의 문제를 풀도록 설계되었습니다.

| 구분 | CPU | GPU |
|---|---|---|
| 코어 | 적고 강하다(수 개~수십 개) | 많고 단순하다(수백~수천 개) |
| 강점 | 복잡한 분기, 순서가 중요한 작업 | 같은 계산을 대량의 데이터에 동시에 적용 |
| 비유 | 어떤 문제든 푸는 소수의 전문가 | 같은 계산을 나눠 맡는 대규모 인원 |
| 예시(교재 장비) | 다중 코어 CPU | GT 1030: CUDA 코어 384개 |

행렬곱은 GPU가 가장 잘하는 종류의 일입니다. `n×n` 행렬 두 개를 곱하면 결과 행렬의 `n²`개 칸이 생기는데, 각 칸은 다른 칸의 결과를 기다리지 않고 **독립적으로** 계산할 수 있습니다. 칸마다 일꾼을 하나씩 붙이면 동시에 끝납니다. LLM의 계산 대부분이 바로 이 행렬곱입니다.

### 이론 성능: 1초에 몇 번 계산하는가

연산 장치의 속도는 FLOPS(Floating-point Operations Per Second, 초당 부동소수점 연산 수)로 잽니다. 이론 최대치는 세 숫자의 곱입니다.

```text
이론 FLOPS = 코어 수 × 동작 클럭 × 클럭당 연산 수
```

| 장치 | 코어 × 클럭 × 클럭당 연산 | 이론 FP32 |
|---|---|---|
| GT 1030 | 384 × 1.468GHz × 2 | 약 1,127 GFLOPS |
| 8코어 CPU(AVX2) | 8 × 4.0GHz × 32 | 약 1,024 GFLOPS |

FMA(Fused Multiply-Add)는 곱셈과 덧셈을 한 번에 처리하는 명령으로, 한 번에 연산 2회로 셉니다. CPU의 32는 FMA 장치 2개가 8칸짜리 벡터(AVX2)를 동시에 처리한 값(2 × 8 × 2)입니다.

GT 1030의 이론 성능은 최신 다중 코어 CPU와 비슷한 수준입니다. 제01장에서 "GT 1030 경로의 가치는 속도보다 경험에 있다"고 말한 근거가 이 표입니다.

### 행렬곱의 연산 수

`n×n` 행렬곱에서 결과 한 칸을 얻으려면 곱셈 `n`번과 덧셈 `n`번이 필요합니다. 칸이 `n²`개이므로 전체 연산 수는 다음과 같습니다.

```text
행렬곱 연산 수 = 2 × n³          예) n = 2048 → 약 172억 번
측정 성능(GFLOPS) = 2 × n³ ÷ 걸린 시간(초) ÷ 10⁹
```

이 공식으로 실측 시간을 성능 숫자로 바꾸면, 서로 다른 장치와 크기를 같은 잣대로 비교할 수 있습니다.

## RAM과 VRAM

계산하려면 데이터가 먼저 연산 장치 가까이에 있어야 합니다. CPU는 시스템 메모리(RAM)를, GPU는 그래픽카드에 붙은 전용 메모리(VRAM)를 씁니다. 둘은 PCIe 버스로 연결되어 있으며, GPU로 계산하려면 데이터를 이 길을 통해 VRAM으로 먼저 옮겨야 합니다.

```text
┌────────── PC ──────────┐            ┌──────── GT 1030 ────────┐
│  CPU  ⇄  RAM(16GB 이상) │ ⇄ PCIe ⇄  │  GPU 코어  ⇄  VRAM(2GB) │
└────────────────────────┘  3.0 ×4    └─────────────────────────┘
```

| 항목 | RAM | VRAM(GT 1030) |
|---|---|---|
| 용량 | 크다(16GB 이상 권장) | 작다(2GB) |
| 연산 장치와의 거리 | CPU 바로 옆 | GPU 바로 옆 |
| GPU 입장의 속도 | PCIe를 거쳐야 해 느리다 | 빠르다(GDDR5 사양 약 48GB/s) |

GT 1030은 메모리 사양이 두 가지입니다. DDR4 사양은 GDDR5 사양보다 메모리 대역폭이 크게 낮아(약 1/3 수준), 같은 이름의 카드라도 실습 속도가 확연히 다릅니다. 제01장 환경 보고서와 함께 자신의 카드 사양을 확인해 두어야 하는 이유입니다.

### LLM 학습 때 메모리에 놓이는 것

모델을 메모리에 "올린다"는 말에는 여러 가지 데이터가 숨어 있습니다.

| 항목 | 내용 | 다루는 장 |
|---|---|---|
| 가중치 | 모델 파라미터 자체 | 제05장 |
| 중간 결과(Activation) | 순전파 과정의 계층별 출력 | 제38장 |
| Gradient | 각 가중치의 기울기(학습 시) | 제23장 |
| Optimizer 상태 | AdamW의 이동 평균 등(학습 시) | 제24장 |
| Logits | 모든 위치에서 어휘 전체에 대한 점수 | 제10장 |

추론만 할 때는 가중치와 약간의 중간 결과면 충분하지만, 학습할 때는 Gradient와 Optimizer 상태가 더해져 필요한 메모리가 몇 배로 늘어납니다. 이 차이가 제3·4부에서 LoRA와 QLoRA가 등장하는 이유입니다.

### 모델 크기를 바이트로 계산하기

가중치 메모리는 **파라미터 수 × 자료형 크기**입니다. Qwen2.5-0.5B의 파라미터는 494,032,768개이며, 자료형에 따라 다음과 같이 달라집니다(다음 실습에서 직접 계산합니다).

| 자료형 | 원소당 크기 | Qwen2.5-0.5B 가중치 |
|---|---|---|
| FP32 | 4바이트 | 1.84GiB |
| FP16·BF16 | 2바이트 | 0.92GiB |
| INT8 | 1바이트 | 0.46GiB |
| NF4 | 0.5바이트 | 0.23GiB(Scale 저장 비용 제외) |

FP32 가중치만으로 1.84GiB입니다. GPU를 쓰기 시작하는 순간 CUDA 실행 환경 자체가 VRAM 일부를 차지하므로, Qwen2.5-0.5B를 FP32 그대로 GT 1030에 올리는 것은 불가능합니다. 이것이 GT 1030 경로에서 0.5B 모델을 4비트(QLoRA)로만 학습하는 이유입니다.

## CUDA와 Compute Capability

CUDA는 NVIDIA GPU에 계산을 시키는 플랫폼입니다. PyTorch가 GPU로 행렬곱을 할 때 실제로 일하는 것은 CUDA 위에서 돌아가는 GPU 전용 코드입니다.

GPU에는 세대마다 **Compute Capability(CC, 연산 능력 세대 번호)**가 붙습니다. 이 번호가 그 GPU가 실행할 수 있는 명령과 기능을 결정합니다.

| CC | 세대 | 예시 | 이 교재에서의 의미 |
|---|---|---|---|
| 6.1 | Pascal | GT 1030 | FP32 사용, NF4 4비트 양자화 가능 |
| 7.5 | Turing | T4, RTX 20 시리즈 | FP16 고속 연산, 8비트 행렬곱 가능 |
| 8.x 이상 | Ampere 이후 | RTX 30 시리즈 이후 | BF16 고속 연산 |

PyTorch 설치 파일에는 지원하는 세대의 GPU 코드만 들어 있습니다. 설치된 PyTorch가 지원하는 세대 목록은 다음 명령으로 확인합니다.

```bash
# 설치된 PyTorch가 포함한 GPU 세대 목록 확인(sm_61이 있어야 GT 1030 사용 가능)
python -c "import torch; print(torch.cuda.get_arch_list())"

# NVIDIA 드라이버 버전과 GPU 상태 확인
nvidia-smi
```

GT 1030은 `sm_61`입니다. 이 항목이 목록에 없으면 GPU가 있어도 PyTorch가 쓰지 못합니다. 제01장에서 PyTorch를 2.14(cu126) 버전으로 고정한 것과, `select_device()`가 이 목록을 확인하는 것은 모두 이 조건 때문입니다.

## 자료형별 연산 속도

16비트 자료형은 32비트보다 메모리를 절반만 씁니다. 최신 GPU에서는 16비트 연산이 32비트보다 훨씬 빠르기도 합니다. 그러나 GT 1030은 반대입니다.

| 자료형 | GT 1030 이론 성능 | FP32 대비 |
|---|---|---|
| FP32 | 약 1,127 GFLOPS | 1 |
| FP16 | 약 17.6 GFLOPS | 1/64 |
| BF16 | 지원하지 않음 | - |

Pascal 세대의 보급형 칩은 16비트 연산 장치를 아주 적게 갖추고 있어, 하드웨어의 FP16 연산 능력이 FP32의 1/64에 불과합니다. 다만 실제 행렬곱 속도는 라이브러리가 16비트 입력을 내부에서 어떻게 처리하는지에 따라 달라질 수 있습니다. 그래서 이 장의 핵심 실습은 GT 1030에서 FP32와 FP16 행렬곱을 **둘 다 실측**합니다. 어느 쪽이든 FP16이 FP32보다 빠를 수는 없으므로, GT 1030 경로의 결론은 같습니다. **저장은 필요하면 16비트로, 계산은 FP32로** 합니다.

## 가용 VRAM 측정

카드에 적힌 2GB를 모두 쓸 수 있는 것은 아닙니다. 실제로 쓸 수 있는 VRAM은 다음 항목을 뺀 나머지입니다.

| 차지하는 것 | 내용 | 줄이는 방법 |
|---|---|---|
| CUDA 컨텍스트 | GPU를 처음 사용할 때 실행 환경이 확보하는 영역 | 피할 수 없음, 측정해서 예산에 반영 |
| 화면 출력 | 모니터를 GT 1030에 연결한 경우 바탕화면 표시용 | 내장 그래픽 또는 원격 접속(SSH) 사용 |
| 다른 프로그램 | 다른 프로세스가 GPU를 사용 중인 경우 | `nvidia-smi`로 확인 후 종료 |

PyTorch에서는 세 가지 함수로 VRAM을 확인합니다.

| 함수 | 알려 주는 값 |
|---|---|
| `mem_get_info()` | 지금 비어 있는 VRAM과 전체 VRAM |
| `memory_allocated()` | PyTorch 텐서가 실제로 쓰고 있는 양 |
| `max_memory_allocated()` | 실행 중 가장 많이 쓴 순간의 양(학습 예산 검증에 사용) |

세 함수는 모두 `torch.cuda` 안에 있습니다.

`nvidia-smi`에 표시되는 사용량은 PyTorch가 텐서용으로 미리 확보해 둔 여유 공간과 CUDA 컨텍스트까지 포함하므로 `memory_allocated()`보다 큽니다. 학습 예산은 두 값을 함께 보고 판단합니다.

## 핵심 실습

두 개의 실습으로 이 장의 두 감각, 계산 속도와 메모리 크기를 숫자로 확인합니다.

### 실습 1. 행렬곱 속도 측정

행렬 크기를 256부터 2048까지 키우며 행렬곱 시간을 재고, GFLOPS와 정확도를 함께 기록합니다. GPU가 있으면 FP32와 FP16도 측정합니다.

파일명: `examples/ch02/bench_matmul.py`

```python
# 제02장 핵심 실습 1: 행렬곱 크기에 따른 CPU·GPU 연산 속도 측정
#
# 실행: python examples/ch02/bench_matmul.py
# 결과: 화면 측정표 + examples/ch02/bench_matmul.csv (+ matplotlib이 있으면 bench_matmul.png)

import csv
import statistics
import sys
import time
from pathlib import Path

sys.path.insert(0, str(Path(__file__).resolve().parents[1]))

import torch  # noqa: E402
from common.device import select_device  # noqa: E402

SIZES = [256, 512, 1024, 2048]   # 정사각 행렬의 한 변 크기 n
REPEAT = 5                        # 같은 측정을 반복해 중앙값을 사용


def matmul_flops(n: int) -> int:
    """n×n 행렬곱의 부동소수점 연산 수: 곱셈 n³ + 덧셈 n³ = 2n³."""
    return 2 * n ** 3


def synchronize(device: str) -> None:
    """GPU는 명령을 예약만 하고 바로 돌아오므로, 실제 완료까지 기다린다."""
    if device == "cuda":
        torch.cuda.synchronize()


def time_matmul(n: int, device: str, dtype: torch.dtype, repeat: int = REPEAT) -> float:
    """행렬곱 한 번에 걸린 시간(초)의 중앙값을 돌려준다."""
    torch.manual_seed(0)
    a = torch.randn(n, n, device=device, dtype=dtype)
    b = torch.randn(n, n, device=device, dtype=dtype)

    a @ b                 # 워밍업: 첫 실행의 준비 시간을 측정에서 제외
    synchronize(device)

    times = []
    for _ in range(repeat):
        start = time.perf_counter()
        a @ b
        synchronize(device)
        times.append(time.perf_counter() - start)
    return statistics.median(times)


def relative_error(n: int, device: str, dtype: torch.dtype) -> float:
    """장치·자료형의 결과를 CPU FP64(기준값)와 비교한 최대 상대오차."""
    torch.manual_seed(0)
    a = torch.randn(n, n, dtype=torch.float64)
    b = torch.randn(n, n, dtype=torch.float64)
    reference = a @ b
    actual = (a.to(device, dtype) @ b.to(device, dtype)).to("cpu", torch.float64)
    return ((actual - reference).abs().max() / reference.abs().max()).item()


def run_configs() -> list:
    """측정할 (장치, 자료형) 조합: CPU FP32는 항상, GPU가 있으면 FP32·FP16 추가."""
    configs = [("cpu", torch.float32)]
    device, _ = select_device(verbose=False)
    if device == "cuda":
        configs += [("cuda", torch.float32), ("cuda", torch.float16)]
    return configs


def main() -> None:
    rows = []
    print(f"{'장치':<6}{'자료형':<10}{'n':>6}{'시간(ms)':>12}{'GFLOPS':>10}{'상대오차':>12}")
    for device, dtype in run_configs():
        name = str(dtype).replace("torch.", "")
        for n in SIZES:
            seconds = time_matmul(n, device, dtype)
            gflops = matmul_flops(n) / seconds / 1e9
            error = relative_error(n, device, dtype)
            rows.append([device, name, n, seconds * 1e3, gflops, error])
            print(f"{device:<6}{name:<10}{n:>6}{seconds * 1e3:>12.2f}{gflops:>10.1f}{error:>12.1e}")

    out = Path(__file__).with_name("bench_matmul.csv")
    with out.open("w", newline="", encoding="utf-8") as f:
        writer = csv.writer(f)
        writer.writerow(["device", "dtype", "n", "ms", "gflops", "rel_error"])
        writer.writerows(rows)
    print(f"\n측정표 저장: {out.name}")

    try:
        import matplotlib
        matplotlib.use("Agg")
        import matplotlib.pyplot as plt
    except ImportError:
        print("matplotlib이 없어 그래프는 생략합니다.")
        return

    for device, name in sorted({(r[0], r[1]) for r in rows}):
        points = [(r[2], r[4]) for r in rows if r[0] == device and r[1] == name]
        plt.plot([p[0] for p in points], [p[1] for p in points], marker="o",
                 label=f"{device} {name}")
    plt.xscale("log", base=2)
    plt.xlabel("matrix size n")
    plt.ylabel("GFLOPS")
    plt.ylim(bottom=0)   # 세로축을 0부터 시작해 차이를 과장하지 않는다
    plt.legend()
    plt.grid(True, alpha=0.3)
    png = Path(__file__).with_name("bench_matmul.png")
    plt.savefig(png, dpi=120, bbox_inches="tight")
    print(f"그래프 저장: {png.name}")


if __name__ == "__main__":
    main()
```

GT 1030 경로에서는 `cuda float32`, `cuda float16` 줄이 추가됩니다(교재 검증 환경에서 미검증). 이론값을 기준으로 하면 FP32는 수백 GFLOPS, FP16은 그보다 훨씬 낮은 값이 예상됩니다. 자신의 측정값을 위 이론 성능표와 비교해 보세요.

**핵심 코드 풀이**

- `matmul_flops(n)`은 `2 × n³`을 돌려줍니다. 측정 시간으로 나누면 장치와 크기에 관계없이 비교할 수 있는 GFLOPS가 됩니다.
- `synchronize()`는 GPU 측정의 핵심입니다. GPU는 명령을 받으면 계산이 끝나기 전에 바로 다음 줄로 넘어가므로, 완료를 기다리지 않고 시간을 재면 실제보다 훨씬 빠른 엉터리 숫자가 나옵니다.
- `time_matmul()`은 첫 실행을 측정에서 빼고(워밍업), 5번 잰 값의 중앙값을 씁니다. 첫 실행에는 준비 작업 시간이 섞이고, 한 번만 재면 우연한 지연에 흔들리기 때문입니다.
- `relative_error()`는 같은 행렬을 CPU의 FP64(64비트)로 계산한 값을 기준으로 삼아 정확도를 잽니다. 속도만 보고 자료형을 고르면 안 되므로, 빠르기와 정확도를 한 표에 함께 남깁니다.

**결과 읽기**

- 교재 검증 환경의 2코어 CPU는 약 300 GFLOPS를 냈습니다. 행렬 크기가 달라져도 성능이 비슷한 것은, 이 크기 범위에서 CPU의 행렬곱 라이브러리가 연산 장치를 고르게 채우고 있다는 뜻입니다.
- 상대오차는 모두 1e-6 수준입니다. FP32의 유효 숫자는 약 7자리이므로, 이 정도 오차는 FP32가 표현할 수 있는 정밀도의 한계와 일치합니다.
- `n`이 두 배가 되면 시간은 약 8배가 됩니다. 연산 수가 `n³`에 비례하기 때문입니다(0.87ms → 7.42ms → 56.86ms).

### 실습 2. 모델 메모리 계산과 실측

Qwen2.5-0.5B의 공식 설정값만으로 파라미터 수와 메모리를 계산하고, 실제 장치에 텐서를 올려 계산이 맞는지 확인합니다.

파일명: `examples/ch02/memory_budget.py`

```python
# 제02장 핵심 실습 2: 모델 메모리 계산과 가용 메모리 측정
#
# 실행: python examples/ch02/memory_budget.py
# 내용: Qwen2.5-0.5B 가중치·Logits 메모리를 계산하고, 실제 장치에 텐서를 올려 계산값과 비교한다.

import sys
from pathlib import Path

sys.path.insert(0, str(Path(__file__).resolve().parents[1]))

import torch  # noqa: E402
from common.device import select_device  # noqa: E402

MIB = 2 ** 20
GIB = 2 ** 30

# Qwen2.5-0.5B-Instruct 공식 config.json 값
QWEN05 = {
    "hidden": 896,
    "intermediate": 4864,
    "layers": 24,
    "heads": 14,
    "kv_heads": 2,
    "vocab": 151936,
}

# 자료형별 원소 하나의 크기(바이트). NF4는 4비트 = 0.5바이트(Scale 저장 비용 제외)
BYTES_PER_PARAM = {"FP32": 4, "FP16/BF16": 2, "INT8": 1, "NF4": 0.5}


def count_qwen_params(c: dict) -> int:
    """config 값만으로 전체 파라미터 수를 계산한다(Embedding·LM Head 공유는 한 번만)."""
    h, i = c["hidden"], c["intermediate"]
    kv = c["kv_heads"] * (h // c["heads"])                 # K·V 출력 차원 = 2 × 64 = 128
    attention = (h * h + h) + 2 * (h * kv + kv) + h * h    # q(+bias), k·v(+bias), o
    mlp = 3 * h * i                                        # gate, up, down
    norms = 2 * h                                          # Attention 앞·FFN 앞 RMSNorm
    embedding = c["vocab"] * h
    return embedding + c["layers"] * (attention + mlp + norms) + h   # 마지막 + h: Final Norm


def logits_bytes(seq_len: int, vocab: int, batch: int = 1, bytes_per: int = 4) -> int:
    """Logits 텐서 [batch, seq, vocab]의 크기(바이트)."""
    return batch * seq_len * vocab * bytes_per


def read_meminfo_gib(field: str) -> float:
    """/proc/meminfo의 항목(예: MemAvailable)을 GiB로 읽는다."""
    with open("/proc/meminfo", encoding="utf-8") as f:
        for line in f:
            if line.startswith(field + ":"):
                return int(line.split()[1]) * 1024 / GIB
    return -1.0


def measure_allocation(device: str, mib: int = 256) -> tuple:
    """지정한 크기의 FP32 텐서를 만들고 (계산값, 실제 증가량)을 바이트로 돌려준다."""
    numel = mib * MIB // 4
    expected = numel * 4
    if device == "cuda":
        torch.cuda.synchronize()
        before = torch.cuda.memory_allocated()
        x = torch.empty(numel, dtype=torch.float32, device="cuda")
        actual = torch.cuda.memory_allocated() - before
    else:
        x = torch.empty(numel, dtype=torch.float32)
        actual = x.element_size() * x.numel()
    del x
    return expected, actual


def main() -> None:
    params = count_qwen_params(QWEN05)
    print(f"Qwen2.5-0.5B 파라미터 수: {params:,}")
    print("\n[가중치 메모리]")
    for name, size in BYTES_PER_PARAM.items():
        print(f"  {name:<10}: {params * size / GIB:6.2f} GiB")

    print("\n[Logits 메모리, Batch 1, FP32]")
    for seq in (128, 256, 512, 1024):
        print(f"  시퀀스 {seq:>4}: {logits_bytes(seq, QWEN05['vocab']) / MIB:7.1f} MiB")

    device, _ = select_device(verbose=False)
    print(f"\n[실측: {device}]")
    if device == "cuda":
        free_b, total_b = torch.cuda.mem_get_info(0)
        print(f"  전체 VRAM          : {total_b / MIB:8.0f} MiB")
        print(f"  사용 가능 VRAM     : {free_b / MIB:8.0f} MiB")
        print(f"  이미 사용 중       : {(total_b - free_b) / MIB:8.0f} MiB (CUDA 컨텍스트·화면 출력 등)")
    else:
        print(f"  전체 RAM           : {read_meminfo_gib('MemTotal'):6.1f} GiB")
        print(f"  사용 가능 RAM      : {read_meminfo_gib('MemAvailable'):6.1f} GiB")

    expected, actual = measure_allocation(device)
    verdict = "일치" if expected == actual else "불일치"
    print(f"  256MiB 텐서 할당   : 계산 {expected / MIB:.0f} MiB, 실제 {actual / MIB:.0f} MiB → {verdict}")


if __name__ == "__main__":
    main()
```

- `measure_allocation()`은 계산을 실제로 확인합니다. GPU에서는 `memory_allocated()`의 증가량을, CPU에서는 텐서의 원소 수와 원소 크기를 비교합니다.

**결과 읽기:** 1.2절의 GT 1030 기준(QLoRA 시퀀스 256, Batch 1)은 바로 이 계산에서 나왔습니다. NF4 가중치(약 0.23GiB)는 작지만, 양자화되지 않는 Embedding과 시퀀스 256의 Logits(148.4MiB, 역전파 시 여러 배로 증가)가 더해지면 2GB가 금세 찹니다.

from pathlib import Path

import torch

# ── 1. 계산식 ───────────────────────────────────────────────────────────

def test_matmul_flops():
    # 2×2 행렬곱: 결과 4칸 × (곱셈 2 + 덧셈 2) = 16 = 2 × 2³
    assert bench_matmul.matmul_flops(2) == 16
    assert bench_matmul.matmul_flops(1024) == 2 * 1024 ** 3


def test_qwen_param_count_matches_official_size():
    # Qwen2.5-0.5B: 공식 표기 0.49B, Embedding은 공유 텐서로 한 번만 계산
    params = memory_budget.count_qwen_params(memory_budget.QWEN05)
    assert params == 494_032_768


def test_qwen_param_count_matches_torch_modules():
    # 같은 구조를 실제 PyTorch 계층으로 만들어 파라미터 수를 세어 대조한다(1개 계층).
    c = memory_budget.QWEN05
    h, i, kv = c["hidden"], c["intermediate"], c["kv_heads"] * (c["hidden"] // c["heads"])
    layer = torch.nn.ModuleList([
        torch.nn.Linear(h, h), torch.nn.Linear(h, kv), torch.nn.Linear(h, kv),   # q, k, v (+bias)
        torch.nn.Linear(h, h, bias=False),                                         # o
        torch.nn.Linear(h, i, bias=False), torch.nn.Linear(h, i, bias=False),      # gate, up
        torch.nn.Linear(i, h, bias=False),                                         # down
    ])
    per_layer = sum(p.numel() for p in layer.parameters()) + 2 * h               # + RMSNorm 2개
    expected = c["vocab"] * h + c["layers"] * per_layer + h
    assert memory_budget.count_qwen_params(c) == expected


def test_logits_bytes():
    # 시퀀스 256 × 어휘 151,936 × 4바이트
    assert memory_budget.logits_bytes(256, 151936) == 155_582_464


def test_fp32_weights_exceed_2gib_budget_with_context():
    # FP32 가중치만 약 1.84GiB → CUDA 컨텍스트를 더하면 GT 1030 2GB에 들어가지 않는다.
    params = memory_budget.count_qwen_params(memory_budget.QWEN05)
    assert 1.8 < params * 4 / 2 ** 30 < 1.9

def test_allocation_matches_calculation():
    device, _ = select_device(verbose=False)
    expected, actual = memory_budget.measure_allocation(device, mib=16)
    assert expected == actual

## 핵심 정리

- CPU는 소수의 강한 코어, GPU는 다수의 단순한 코어로 일합니다. 칸마다 독립적으로 계산할 수 있는 행렬곱은 GPU에 잘 맞습니다.
- 성능은 `2 × n³ ÷ 시간`으로 GFLOPS를 계산해 비교합니다. GPU 시간을 잴 때는 반드시 완료를 기다려야(`synchronize`) 합니다.
- 메모리는 **파라미터 수 × 자료형 크기**로 계산합니다. Qwen2.5-0.5B는 FP32로 1.84GiB라 GT 1030에 그대로 올릴 수 없습니다.
- 어휘가 큰 LLM에서는 Logits가 시퀀스 길이에 비례해 커지는 숨은 메모리 소비자입니다.
- GT 1030(CC 6.1)은 FP16 연산 능력이 낮고 BF16을 지원하지 않으므로, 계산은 FP32로 합니다.

**다음 장 연결:** 제03장에서는 이 장에서 메모리 크기를 계산할 때 쓴 `[batch, 시퀀스, 어휘]` 같은 모양, 즉 Tensor의 차원과 Shape를 본격적으로 다룹니다. LLM의 모든 데이터는 이 모양을 읽는 데서 시작합니다.
