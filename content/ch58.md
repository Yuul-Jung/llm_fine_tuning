## 장 개요

지금까지 모델은 메모리 8GB의 교재 검증 컴퓨터에서 실행했습니다. 실제로 모델을 쓰는 곳은 더 작은 장치일 수 있습니다. 그래픽 메모리 2GB의 GT 1030, 메모리 4GB의 Raspberry Pi, 인터넷이 없는 현장의 작은 컴퓨터입니다. **온디바이스 AI**는 데이터를 기기 밖으로 보내지 않고 그 기기 안에서 모델을 실행하는 것이며, 가장 먼저 부딪히는 벽은 메모리입니다.

이 장은 모델 실행에 필요한 메모리를 가중치와 KV Cache로 나눠 계산하고, 장치별로 어떤 형식과 문맥 길이까지 실을 수 있는지 판정합니다. 그리고 교재 검증 CPU에서 속도와 메모리를 측정 조건과 함께 기록해, 계산값과 실측값을 맞춰 봅니다.

| 구분 | 내용 |
|---|---|
| 핵심 질문 | 어떤 장치에서 어떤 모델을 얼마나 긴 문맥으로 실행할 수 있는지 어떻게 미리 판정하는가 |
| 실습 결과물 | 문맥 길이별 KV Cache, 형식별 가중치 크기, 장치별 탑재 판정, CPU 속도·메모리 실측과 계산 대조 |
| 실습 파일 | `examples/ch58/`의 `ondevice.py`, `test_ch58.py`, `measure.json` |
| 선수 장 | 제20장(KV Cache), 제33~36장(양자화 형식), 제52장(병합 모델) |

```text
필요한 메모리 = 가중치(파라미터 수 × 형식의 평균 비트) + KV Cache(토큰당 바이트 × 문맥 길이) + 연산 버퍼·운영체제
판정: 필요한 메모리 ≤ 장치 메모리 × 75%     (25%는 운영체제·연산 버퍼·단편화 몫)
```

## 클라우드·로컬·엣지

| 실행 위치 | 데이터 | 제약 |
|---|---|---|
| 클라우드 | 외부 서버로 보낸다 | 네트워크·비용·데이터 반출 규정 |
| 로컬(PC·사내 서버) | 조직 안에 머문다 | 장비 성능, 직접 운영 |
| 엣지(작은 기기) | 기기 안에 머문다 | 메모리·전력·발열이 가장 빡빡하다 |

로컬과 엣지 실행의 장점은 데이터가 밖으로 나가지 않고, 네트워크 없이도 동작하며, 응답 시간이 일정하다는 것입니다. 대가는 장치의 메모리와 연산 속도에 맞춰 모델 크기, 형식, 문맥 길이를 줄여야 한다는 점입니다. 그래서 실행 전에 "실을 수 있는가"를 계산으로 먼저 판정합니다.

## 메모리 제약과 KV Cache

추론 메모리의 큰 몫은 둘입니다. **가중치**는 모델이 정해지면 고정이고, **KV Cache**는 대화가 길어질수록 커집니다(제20장). 토큰 하나를 처리할 때마다 모든 층이 그 토큰의 Key와 Value를 저장해 두기 때문입니다.

```text
KV Cache(바이트) = 2(K, V) × 층 수 × KV 헤드 수 × head_dim × 자료형 바이트 × 토큰 수
```

Qwen2.5-0.5B는 KV 헤드가 2개뿐이라(GQA) 토큰당 KV Cache가 작습니다. 가중치 형식은 제33~36장의 양자화와 같은 원리이며, 로컬 실행 도구의 대표 형식은 32개씩 묶은 블록마다 Scale을 둡니다.

| 형식 | 블록 구조(32개당) | 평균 비트 |
|---|---|---|
| Q8_0 | INT8 32개 + FP16 Scale 1개 = 34바이트 | 8.5 |
| Q4_0 | 4비트 32개 + FP16 Scale 1개 = 18바이트 | 4.5 |

Scale을 블록마다 두므로 평균 비트는 8과 4보다 조금 큽니다. 이 장의 가중치 크기는 이 구조로 계산한 값이며, 실제 파일은 1차원 텐서(편향·RMSNorm)를 F32로 두고 메타데이터가 더해져 조금 큽니다. 제55장에서 만든 실제 파일은 Q8_0 506MiB, Q4_0 271MiB로, 이 장의 계산(501MiB, 265MiB)보다 5~6MiB 컸습니다.

## 장치별 실행

장치마다 쓸 수 있는 메모리에서 운영체제와 연산 버퍼 몫(이 장은 25%로 둠)을 빼고, 가중치와 KV Cache가 그 안에 들어가는지 봅니다. 판정은 메모리만 따진 것이며, 들어간다고 빠른 것은 아닙니다. 예를 들어 GT 1030은 FP16 가중치가 메모리에 들어가도 FP16 연산이 FP32의 1/64 속도라(제32장) FP16으로 계산하면 매우 느립니다. 양자화 형식은 실행 도구가 정수 연산이나 FP32로 계산하므로 이 문제를 피할 수 있습니다(구체적인 계산 방식은 실행 도구와 GPU 세대에 따라 다르며, GT 1030에서의 속도는 미검증).

교재 검증 환경에는 GT 1030과 Raspberry Pi가 없으므로, 이 장의 장치별 실행은 계산으로 판정하고 실측은 CPU에서만 했습니다. 다른 장치에서 같은 측정을 하면 같은 형식의 표로 결과를 비교할 수 있습니다.

## 측정과 선정 기준

속도와 메모리는 측정 조건에 따라 크게 달라지므로, 숫자와 함께 조건을 반드시 기록합니다.

| 기록할 것 | 이유 |
|---|---|
| 장치·스레드 수·라이브러리 판 | 같은 모델도 환경에 따라 속도가 몇 배 달라진다 |
| 문맥 길이와 생성 토큰 수 | 문맥이 길수록 토큰당 계산과 KV Cache가 늘어난다 |
| 예열 여부 | 첫 실행은 메모리 할당 때문에 느리다 |
| 메모리 측정 방법 | 파일을 메모리에 연결만 해 두는 방식(mmap)은 읽기 전까지 메모리를 덜 쓴 것처럼 보인다 |

모델을 고를 때는 **품질 기준을 먼저 통과한 것 중에서** 장치에 들어가고 속도 요구를 만족하는 가장 작은 형식을 고릅니다. 속도가 빨라도 품질 기준(제43장)을 넘지 못하면 후보가 아닙니다. 형식별 품질은 제55장에서 비교합니다.

## 핵심 실습

파일명: `examples/ch58/ondevice.py`

```python
# 제58장 핵심 실습: 장치별 메모리 예산(가중치 + KV Cache + 여유)을 계산하고, CPU에서 속도·메모리를 측정한다
#
# 실행: python examples/ch58/ondevice.py   (제52장의 병합 모델 필요, CPU 약 2분)
#
# GGUF 형식의 크기는 블록 구조로 계산한 값이다(Q8_0: 32개당 34바이트, Q4_0: 32개당 18바이트).
# llama.cpp·GT 1030·Raspberry Pi 실측은 교재 검증 환경에서 하지 않았다(미검증).

import json
import platform
import resource
import sys
import time
from pathlib import Path

HERE = Path(__file__).resolve().parent
ROOT = HERE.parents[1]
for p in (HERE.parent, HERE.parent / "ch20"):
    sys.path.insert(0, str(p))

import torch  # noqa: E402

from common.device import select_device  # noqa: E402
from sampling_kv import kv_bytes_per_token  # noqa: E402        (제20장)

MERGED = ROOT / "models" / "fpga_merged_v1"
OUT = HERE / "measure.json"
MiB = 2 ** 20
BITS = {"FP32": 32, "FP16": 16, "Q8_0": 34 * 8 / 32, "Q4_0": 18 * 8 / 32}     # 가중치 하나당 평균 비트
DEVICES = {"GT 1030": 2048, "Raspberry Pi 4GB": 4096, "교재 CPU 8GB": 8192}  # 쓸 수 있는 메모리 MiB
RESERVE = 0.25                                                                 # 운영체제·연산 버퍼 몫


def weight_mib(n_params: int, fmt: str) -> float:
    return n_params * BITS[fmt] / 8 / MiB


def kv_mib(cfg, tokens: int, bytes_per: int) -> float:
    return kv_bytes_per_token(cfg, bytes_per) * tokens / MiB


def fits(total_mib: float, device_mib: int) -> bool:
    return total_mib <= device_mib * (1 - RESERVE)


def rss_mib() -> float:
    return resource.getrusage(resource.RUSAGE_SELF).ru_maxrss / 1024        # 리눅스: KiB 단위


def main() -> None:
    from transformers import AutoConfig, AutoModelForCausalLM, AutoTokenizer
    cfg = AutoConfig.from_pretrained(MERGED)
    n = 494_032_768                                            # 제52장 병합 모델 파라미터 수
    print("── 1. KV Cache: 토큰 하나당과 문맥 길이별(Qwen2.5-0.5B) ──")
    print(f"  토큰당 FP32 {kv_bytes_per_token(cfg, 4):,}B, FP16 {kv_bytes_per_token(cfg, 2):,}B "
          f"(2 × {cfg.num_hidden_layers}층 × KV 헤드 {cfg.num_key_value_heads} × 64 × 자료형)")
    for t in (512, 2048, 8192, 32768):
        print(f"  {t:>6}토큰  FP32 {kv_mib(cfg, t, 4):7.1f}MiB  FP16 {kv_mib(cfg, t, 2):7.1f}MiB")

    print("\n── 2. 장치별 탑재 판정(가중치 + FP16 KV Cache, 가용의 75% 이내) ──")
    print(f"  가중치: " + ", ".join(f"{f} {weight_mib(n, f):.0f}MiB" for f in BITS))
    table = {}
    for dev, mem in DEVICES.items():
        row = {}
        for fmt in BITS:
            for t in (2048, 32768):
                row[f"{fmt}@{t}"] = fits(weight_mib(n, fmt) + kv_mib(cfg, t, 2), mem)
        table[dev] = row
        ok = [k for k, v in row.items() if v]
        print(f"  {dev:<17}가능: {', '.join(ok) if ok else '없음'}")

    print("\n── 3. CPU 실측(병합 모델 FP32, Hugging Face, Greedy 64토큰) ──")
    device, _ = select_device()
    tok = AutoTokenizer.from_pretrained(MERGED)
    t0 = time.time()
    model = AutoModelForCausalLM.from_pretrained(MERGED, dtype=torch.float32).to(device).eval()
    load_s = time.time() - t0
    rss_loaded = rss_mib()
    results = []
    for ctx in (32, 512):
        ids = torch.randint(1000, 20000, (1, ctx), generator=torch.Generator().manual_seed(0)).to(device)
        with torch.no_grad():
            model.generate(ids, max_new_tokens=4, do_sample=False, pad_token_id=tok.pad_token_id)   # 예열
            t1 = time.time()
            out = model.generate(ids, max_new_tokens=64, min_new_tokens=64, do_sample=False,
                                 pad_token_id=tok.pad_token_id, return_dict_in_generate=True)
            dt = time.time() - t1
        kv = out.past_key_values
        kv_real = sum(t.numel() * t.element_size() for layer in kv.layers for t in (layer.keys, layer.values))
        results.append({"ctx": ctx, "tok_per_s": 64 / dt, "kv_mib": kv_real / MiB,
                        "kv_formula_mib": kv_mib(cfg, ctx + 63, 4)})
        print(f"  문맥 {ctx:>3} + 생성 64: {64 / dt:5.1f}토큰/초, KV Cache 실제 {kv_real / MiB:5.2f}MiB"
              f" / 계산 {kv_mib(cfg, ctx + 63, 4):5.2f}MiB")
    print(f"  로딩 {load_s:.1f}초, 최대 메모리(프로세스) 로딩 후 {rss_loaded:.0f}MiB → 생성 후 {rss_mib():.0f}MiB")
    print(f"  측정 조건: {platform.machine()}, 스레드 {torch.get_num_threads()}개, PyTorch {torch.__version__}")
    OUT.write_text(json.dumps({"fits": table, "cpu": results, "load_s": load_s, "rss_mib": rss_mib(),
                               "threads": torch.get_num_threads()}, ensure_ascii=False, indent=1) + "\n",
                   encoding="utf-8")


if __name__ == "__main__":
    main()
```

```bash
python examples/ch58/ondevice.py
```

**결과 읽기**

- **1번**에서 토큰 하나의 KV Cache는 FP32로 24,576바이트(24KiB)입니다. 32,768토큰(Qwen2.5의 최대 문맥)이면 FP32 768MiB, FP16 384MiB로, FP16 기준 Q4_0 가중치(265MiB)보다 큽니다. 긴 문맥에서는 KV Cache가 가중치만큼 중요한 예산 항목이 됩니다.
- **2번**에서 GT 1030(2GB)은 FP32 가중치(1,885MiB)만으로 75% 한도(1,536MiB)를 넘어 FP32로는 실을 수 없고, FP16·Q8_0·Q4_0는 최대 문맥까지 들어갑니다. 다만 FP16은 위에서 본 이유로 GT 1030에서 쓰지 않습니다. Raspberry Pi 4GB와 교재 CPU는 모든 형식이 들어갑니다.
- **3번**에서 실제로 저장된 KV Cache의 크기가 계산과 소수점 둘째 자리까지 같습니다(문맥 + 생성 63토큰분, 마지막 토큰의 KV는 아직 저장 전). 속도는 문맥 32에서 초당 약 10토큰, 문맥 512에서 약 7토큰으로, 문맥이 길수록 느려집니다.
- 로딩 직후 프로세스 메모리는 435MiB였다가 생성 후 2,397MiB가 됩니다. 가중치 파일을 메모리에 연결만 해 두었다가 계산하며 실제로 읽기 때문입니다. 로딩 직후의 값만 보고 "모델이 435MiB를 쓴다"고 판단하면 안 됩니다. 2,397MiB는 FP32 가중치 1,885MiB에 연산 버퍼와 라이브러리를 더한 값입니다.

## 검증과 완료 기준

```python
# 제58장 검증 테스트
#
# 실행: python -m pytest examples/ch58 -q

import json
import sys
from pathlib import Path
from types import SimpleNamespace

HERE = Path(__file__).resolve().parent
sys.path.insert(0, str(HERE))

from ondevice import OUT, fits, kv_mib, weight_mib  # noqa: E402

QWEN = SimpleNamespace(hidden_size=896, num_attention_heads=14, num_key_value_heads=2, num_hidden_layers=24)


def test_kv_cache_formula():
    assert kv_mib(QWEN, 1, 4) * 2 ** 20 == 2 * 24 * 2 * 64 * 4
    assert kv_mib(QWEN, 32768, 2) == 384.0


def test_block_format_sizes():
    n = 32 * 1000
    assert weight_mib(n, "Q8_0") * 2 ** 20 == 1000 * 34 and weight_mib(n, "Q4_0") * 2 ** 20 == 1000 * 18


def test_fit_rule_and_records():
    assert fits(1536, 2048) and not fits(1537, 2048)
    r = json.loads(OUT.read_text(encoding="utf-8"))
    assert not r["fits"]["GT 1030"]["FP32@2048"] and r["fits"]["GT 1030"]["Q4_0@32768"]
    for c in r["cpu"]:
        assert abs(c["kv_mib"] - c["kv_formula_mib"]) < 1e-6                  # 실제 KV Cache = 계산
```

| GT 1030·Raspberry Pi 실측 | 같은 표 형식으로 속도·메모리 측정 | 미검증(장치 없음) |
| GGUF 모델 실행 | 같은 GGUF 모델을 장치별로 실행 | 미검증(GGUF는 제54·55장에서 만들었으나 실행 도구 미설치) |

이 장의 측정은 `select_device()`가 고른 장치(교재 검증 환경은 CPU)에서 Hugging Face 모델로 했습니다. 설계상 장치별 비교는 같은 GGUF 모델로 해야 합니다. GGUF 파일은 제54·55장에서 만들었지만 llama.cpp·Ollama 같은 실행 도구가 교재 검증 환경에 없어, 이번 판은 계산 판정과 Hugging Face 모델의 CPU 실측만 담았습니다.

**완료 기준:** 자신의 장치(또는 다른 PC)의 메모리를 DEVICES에 더해 판정을 다시 하고, 스레드 수를 1과 최대로 바꿔 초당 토큰 수가 어떻게 달라지는지 측정 조건과 함께 기록하며, 테스트 3개를 모두 통과하면 이 장을 마친 것입니다.

## 핵심 정리

- 온디바이스 실행은 데이터를 기기 안에 두는 대신 메모리·속도·전력에 맞춰 모델을 줄여야 합니다. 실행 전에 메모리를 계산으로 판정합니다.
- 필요한 메모리는 가중치 + KV Cache + 여유입니다. KV Cache는 문맥 길이에 비례하며, 긴 문맥에서는 가중치만큼 커집니다.
- 블록 양자화 형식은 Scale 때문에 평균 비트가 조금 큽니다(Q8_0 8.5, Q4_0 4.5).
- 메모리에 들어가는 것과 빠른 것은 다릅니다. GT 1030은 FP16 연산이 매우 느립니다.
- 속도·메모리는 장치, 스레드, 문맥 길이, 예열, 측정 방법과 함께 기록합니다. 파일을 메모리에 연결만 해 두는 방식은 로딩 직후 메모리를 작게 보이게 합니다.

**다음 장 연결:** 제59장(선택)에서는 LLM 추론의 대부분을 차지하는 행렬곱을 하드웨어로 옮깁니다. 제53장에서 꺼낸 k_proj 가중치를 INT8로 만들어 Basys3 FPGA의 자원에 맞춰 보고, 정수 MAC 연산 블록을 Verilog로 설계합니다.
