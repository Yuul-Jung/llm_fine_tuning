# 제6부(51~60장) 적대적 검증 보고서

**검증 일시:** 2026-11-25 · **대상:** `content/ch51.md` ~ `content/ch53.md`, `content/ch57.md` ~ `content/ch60.md`, 해당 `examples/`
**판정 기준:** 통과 / 실패 / 미검증 / 해당 없음 (rule_md 공통 기준)

**범위 주의:** 제54장(GGUF 변환), 제55장(추론용 양자화), 제56장(Ollama 배포)은 **작성하지 못했습니다.** llama.cpp 저장소 복제와 PyPI `gguf` 패키지 설치가 모두 자동 권한 검사에서 거부되었고, GGUF 형식을 직접 구현하는 것은 거부 취지를 피해 가는 일이라 하지 않았습니다. 사용자 허가(또는 사용자 환경에서의 실행)를 기다리며, 허가가 나면 세 장을 쓰고 제58·60장을 판 올림합니다.

## 3. 발견 사항과 조치

| 번호 | 위치 | 문제 | 조치 |
|---|---|---|---|
| 1 | 제46~48·50장 실습 코드(제5부 보고서의 미해결 항목) | 장치를 CPU로 고정해 저장소 규칙 3(`select_device()` 사용)과 어긋남 | 제46장은 `select_device()`로 장치를 고르고, 제47장에 VRAM이 부족하면 CPU로 학습하는 `train_device()`를 두어 제47·48·50장이 사용(FP32 0.5B 학습은 GT 1030에서 CPU). CPU에서 출력이 같음을 제46·47·48(범위 비교)장 재실행으로 확인. 제46장 v02, 제47·48장 v04, 제50장 v03 |
| 2 | 제58장 본문(작성 중) | "양자화 형식은 실행 도구가 FP32로 풀어 계산"이라고 단정. GPU 세대에 따라 정수 연산을 쓰기도 함 | 실행 도구·GPU 세대에 따라 다르다고 고치고 GT 1030 속도는 미검증으로 표시 |
| 3 | 제59장 본문(작성 중) | Decoder 층의 투영 구성을 제18장(정규화와 Residual)으로 잘못 가리킴 | 제20장으로 정정 |
| 4 | 제52장 실습 주석(작성 중) | 확인하지 않은 메모리 수치("약 5GB")를 적음 | 교재 검증 환경 메모리(8GB)에서 실행했다는 사실로 바꿈 |
| 5 | 제57장(작성 중) | Generate API가 System 문구 없이 요청해, 서버에서 기본 영어 문구가 들어감(제44장의 함정) | 서버·클라이언트에 Ollama와 같은 system 항목 추가 |
| 6 | 제51·53·57장(작성 중) | 320px에서 넘침: 긴 파일명 열이 있는 표, 문장 안의 긴 텐서 이름, 검증표의 긴 칸 | 표를 2열로, 텐서 이름을 텍스트 블록으로, 칸 문구 단축 |
| 7 | 제53장(작성 중) | Weight Tying 확인에 메모리 주소 값을 출력해 실행마다 결과가 달라짐(재현 대조 불가) | 주소가 같은지만 출력 |

수정한 게시 장의 판 번호: 제46장 v02, 제47·48장 v04, 제50장 v03. 2~7번은 게시 전에 고쳐 판 번호에 반영하지 않았습니다.

## 5. 남은 확인 사항

- **허가 필요:** GGUF 변환 도구(PyPI `gguf` 또는 llama.cpp)와 Ollama. 허가되면 제54~56장 작성, 제58장 GGUF 실행, 제60장 배포 단계를 채우고 판 올림
- GT 1030: QLoRA 최대 VRAM(계산 895MiB), 추론 속도, Ollama GPU 적재 비율
- 제59장(선택): Icarus Verilog 또는 Vivado에서 Testbench PASS와 합성 자원·타이밍
- 데이터 확대: validation·test 각 6문항, 빈 주제의 새 문항(제5부 보고서와 같음)
